# 功能规格说明书：用户管理与基于角色的访问控制

**功能分支**: `002-user-rbac`
**创建日期**: 2026-04-10
**状态**: 已澄清（含前端范围）
**输入**: 用户描述: "为Taskify增加用户管理，角色权限管理"

## 澄清记录

### 2026-04-10 会议

- Q: 现有系统已有 User 模型和预置用户数据（如张明、李伟等），新增用户管理功能应该如何处理这些已有数据？ → A: **替换迁移** - 废弃现有 User 表，创建全新的用户认证系统。预置用户需要重新创建。
- Q: 用户权限是否应该基于「项目成员资格」？ → A: **是，项目成员表** - 创建 project_members 表存储 用户-项目-角色 关系。用户在不同项目有不同角色。
- Q: 是否需要在本次功能中为所有现有接口添加权限验证？ → A: **是，全部添加权限校验** - 所有现有接口都需要验证用户登录状态和项目成员资格。Guest 只能查看，Member 可以操作任务，Owner/Admin 有管理权限。
- Q: 当前是否有邮件发送基础设施？ → A: **无，暂时跳过邮件功能** - 注册时邮箱标记为已验证（演示环境），密码找回暂不支持。后续有邮件基础设施时再补充。
- Q: 「项目管理」是指项目本身的 CRUD（创建、编辑、删除、归档）管理，还是仅指项目级权限控制？ → A: **完整 CRUD** - 包含项目的创建、编辑、删除、归档功能。项目创建者自动成为 Owner，拥有全部管理权限。
- Q: Project Owner 和系统管理员在成员管理上的分工是什么？ → A: **Owner 全权管理** - Project Owner 可以独立管理自己项目的所有成员（添加、移除、修改角色），无需系统管理员介入。系统管理员保留全局管理权限。
- Q: 新增用户认证系统需要前端做哪些页面修改？ → A: **全部新增/替换** - 新增登录页、注册页、个人资料页、管理员用户管理页、管理员角色管理页、替换现有 UserSelect 为登录页、所有页面添加认证守卫。
- Q: 管理员页面（用户管理、角色管理）应该使用什么布局？ → A: **独立管理后台** - 创建独立的管理后台界面（/admin 路径下），包含用户管理、角色管理、权限配置等独立菜单和页面。
- Q: 项目管理（创建、编辑、删除项目）和项目成员管理需要新建前端页面吗？ → A: **是，新增项目页面** - 新增项目管理页面（创建项目对话框、项目列表/卡片、项目设置、成员邀请/管理）。

## 用户场景与测试

### 用户故事 1 - 用户注册与登录 (优先级: P1)

作为一名新用户，我希望创建账户并登录，以便访问 Taskify 系统。

**优先级原因**: 没有身份认证，其他用户管理功能都无法运作。这是整个功能的基础。

**独立测试**: 可以通过创建新用户账户并验证登录/登出流程来完全测试，确保提供对系统的安全访问。

**验收场景**:

1. **假设** 我是一位新访客，**当** 我使用有效邮箱和密码注册时，**那么** 系统创建我的账户并自动登录。
2. **假设** 我已拥有账户，**当** 我使用正确凭据登录时，**那么** 我获得系统访问权限并看到我的项目列表。
3. **假设** 我已登录，**当** 我登出时，**那么** 我的会话被终止并被重定向到登录页面。
4. **假设** 我尝试使用无效凭据登录，**当** 我提交登录表单时，**那么** 我看到错误消息且无法访问系统。

---

### 用户故事 2 - 用户资料管理 (优先级: P2)

作为一名已登录用户，我希望管理我的个人资料信息，以便保持我的账户详细信息最新。

**优先级原因**: 用户需要维护准确的联系信息和偏好设置。

**独立测试**: 可以通过更新用户资料字段（姓名、邮箱、头像）并验证更改是否持久化来完全测试。

**验收场景**:

1. **假设** 我已登录，**当** 我进入我的个人设置页面，**那么** 我看到当前显示的信息。
2. **假设** 我已登录，**当** 我更新我的显示名称，**那么** 新名称在整个系统中显示。
3. **假设** 我已登录，**当** 我更改我的邮箱地址，**那么** 系统向新邮箱发送验证邮件。（注：当前版本跳过邮件发送，邮箱直接标记为已验证）
4. **假设** 我已登录，**当** 我更新我的密码，**那么** 系统在下次登录时要求使用新密码。

---

### 用户故事 3 - 角色管理 (优先级: P2)

作为系统管理员，我希望定义和管理角色，以便控制用户在系统中可以做什么。

**优先级原因**: 角色定义是权限系统的基础。没有定义的角色，权限就无法分配。

**独立测试**: 可以通过创建、编辑和删除自定义角色并验证角色属性被正确存储来完全测试。

**验收场景**:

1. **假设** 我是系统管理员，**当** 我查看角色列表时，**那么** 我看到所有系统预定义角色及其描述。
2. **假设** 我是系统管理员，**当** 我创建新的自定义角色时，**那么** 该角色出现在角色列表中。
3. **假设** 我是系统管理员，**当** 我编辑角色的名称或描述时，**那么** 更改被保存并在整个系统中反映。
4. **假设** 我是系统管理员，**当** 我删除未被任何用户分配的自定义角色时，**那么** 该角色从系统中移除。

---

### 用户故事 4 - 权限配置 (优先级: P2)

作为系统管理员，我希望配置每个角色可以做什么，以便实施最小权限原则。

**优先级原因**: 权限将角色转换为可操作的访问控制。这就是安全如何被执行。

**独立测试**: 可以通过向角色分配权限并验证具有该角色的用户具有预期访问权限来完全测试。

**验收场景**:

1. **假设** 我是系统管理员，**当** 我查看角色的权限时，**那么** 我看到所有可用权限及其当前分配情况。
2. **假设** 我是系统管理员，**当** 我向角色分配权限时，**那么** 具有该角色的用户现在可以执行允许的操作。
3. **假设** 我是系统管理员，**当** 我从角色移除权限时，**那么** 具有该角色的用户失去对该操作的访问权限。
4. **假设** 我是系统管理员，**当** 我查看所有可用权限时，**那么** 权限按资源类型分组（如用户、项目、任务、评论）。

---

### 用户故事 5 - 用户角色分配 (优先级: P1)

作为系统管理员，我希望向用户分配角色，以便他们具有适当的访问级别。

**优先级原因**: 没有角色分配，用户无法获得权限。这将用户连接到角色系统。

**独立测试**: 可以通过向用户分配角色并验证用户获得预期权限来完全测试。

**验收场景**:

1. **假设** 我是系统管理员，**当** 我查看用户详情时，**那么** 我看到他们当前的角色分配。
2. **假设** 我是系统管理员，**当** 我向用户分配角色时，**那么** 用户立即获得该角色的权限。
3. **假设** 我是系统管理员，**当** 我更改用户的角色时，**那么** 用户的权限更新为匹配新角色。
4. **假设** 我是系统管理员，**当** 我从用户移除角色时，**那么** 用户失去该角色的所有权限。

---

### 用户故事 6 - 项目管理 (优先级: P1)

作为已登录用户，我希望创建和管理项目，以便组织和协作工作内容。

**优先级原因**: 项目是任务和成员管理的容器，没有项目管理就无法组织工作。

**独立测试**: 可以通过创建新项目、编辑项目信息、删除项目并验证系统响应来完全测试。

**验收场景**:

### 用户故事 7 - 项目成员邀请与管理 (优先级: P1)

作为项目 Owner，我希望邀请和管理项目成员，以便团队协作。

**优先级原因**: 项目需要多个成员参与，Owner 需要能够添加和移除成员。

**独立测试**: 可以通过添加项目成员、更改成员角色、移除成员并验证权限变化来完全测试。

**验收场景**:

2. **假设** 我是项目 Owner，**当** 我将成员角色从 Member 改为 Guest 时，**那么** 该成员权限立即更新为 Guest 级别。
3. **假设** 我是项目 Owner，**当** 我从项目中移除成员时，**那么** 该成员失去对项目的所有访问权限，但他们的任务和评论保留。
4. **假设** 我是项目 Member 或 Guest，**当** 我查看项目成员列表时，**那么** 我看到所有成员及其各自角色。

### 用户故事 12 - 前端访问控制执行 (优先级: P1)

作为前端用户，我希望系统根据我的角色显示和禁用相应操作，以便我不会看到或尝试无权执行的操作。

**优先级原因**: 前端权限控制提升用户体验，避免用户看到无权限的按钮后点击导致后端拒绝。

**独立测试**: 可以通过使用不同角色登录并验证页面元素可见性和禁用状态。

**验收场景**:

1. **假设** 我是 Guest 登录，**当** 我查看项目看板页面，**那么** 我看不到新建任务、编辑任务按钮，只能查看。
2. **假设** 我是 Member 登录，**当** 我查看项目看板页面，**那么** 我可以创建和编辑任务，但看不到删除项目按钮。
3. **假设** 我未登录，**当** 我直接访问项目页面 URL，**那么** 系统重定向我到登录页面。

作为用户，我希望系统强制执行访问控制，以便我只能执行角色允许的操作。

**优先级原因**: 这是核心安全机制。没有执行，权限系统毫无意义。

**独立测试**: 可以通过尝试使用不足权限执行操作并验证它们被阻止来完全测试。

**验收场景**:

1. **假设** 我是普通成员用户，**当** 我尝试访问管理功能时，**那么** 系统拒绝访问并显示错误。
2. **假设** 我是项目成员，**当** 我尝试删除项目时，**那么** 系统拒绝访问（只有项目所有者或管理员可以）。
3. **假设** 我已登出，**当** 我尝试访问任何受保护页面时，**那么** 系统将我重定向到登录页面。
4. **假设** 我是项目的访客用户，**当** 我尝试创建任务时，**那么** 系统拒绝访问（访客只能查看）。

## 需求

### 功能需求

- **FR-001**: 系统必须允许新用户使用邮箱和密码注册。
- **FR-002**: 系统必须通过邮箱和密码凭据对用户进行身份认证。
- **FR-003**: 系统必须允许用户登出并终止其会话。
- **FR-004**: 系统必须允许用户更新自己的个人资料（姓名、头像）。
- **FR-005**: 系统必须允许用户在当前密码验证后更改密码。
- **FR-006**: 系统必须提供预定义角色：系统管理员、项目所有者、成员、访客。
- **FR-007**: 系统必须允许管理员创建具有描述性名称的自定义角色。
- **FR-008**: 系统必须允许管理员删除未被任何用户分配的自定义角色。
- **FR-009**: 系统不得允许删除预定义系统角色（管理员、所有者、成员、访客）。
- **FR-010**: 系统必须定义按资源分组的权限：用户（查看、管理）、项目（查看、创建、编辑、删除）、任务（查看、创建、编辑、移动、删除）、评论（查看、创建、编辑、删除）。
- **FR-011**: 系统必须允许管理员向角色分配任何组合的权限。
- **FR-012**: 系统必须允许管理员向用户分配角色。
- **FR-013**: 系统必须基于用户角色权限在所有受保护操作上强制执行访问控制。
- **FR-014**: 系统必须拒绝非管理员用户访问管理功能。
- **FR-015**: 系统必须在访问受保护资源时将未认证用户重定向到登录页面。
- **FR-016**: 系统必须阻止非成员用户访问他们不是成员的项目，除非他们是管理员。
- **FR-017**: 系统必须记录安全相关事件（登录、登出、权限更改、失败的访问尝试）。
- **FR-018**: 系统必须基于用户身份认证和项目成员资格对所有现有 API 端点（项目、任务、评论）进行访问控制改造。
- **FR-019**: 系统必须允许已登录用户创建新项目，并在创建时自动将该用户分配为项目 Owner。
- **FR-020**: 系统必须允许项目 Owner 编辑项目名称和描述。
- **FR-021**: 系统必须允许项目 Owner 删除项目，删除前要求确认，删除后项目及其所有任务永久移除。
- **FR-022**: 系统必须允许项目 Owner 归档项目，归档后项目不显示在活动项目列表中但数据保留。
- **FR-023**: 系统必须允许项目 Owner 在自己的项目内添加、移除成员并修改成员角色，无需系统管理员介入。
- **FR-024**: 前端必须提供登录页面，支持邮箱和密码输入及提交。
- **FR-025**: 前端必须提供注册页面，支持新用户创建账户。
- **FR-026**: 前端必须在所有页面添加认证守卫，未登录用户访问受保护路径时重定向到登录页。
- **FR-027**: 前端必须提供 /admin 路径下的管理后台，包含用户管理、角色管理、权限配置页面。
- **FR-028**: 前端必须根据用户角色显示/隐藏操作按钮和菜单项（Guest 隐藏创建/编辑/删除，Member 隐藏项目删除等）。
- **FR-029**: 前端必须提供项目管理页面，支持创建、编辑、归档项目和项目成员邀请/管理。

### 关键实体

- **User（用户）**: 表示系统用户。属性：唯一标识符、邮箱地址、显示名称、头像 URL、密码哈希、创建时间戳、最近登录时间戳、邮箱已验证（布尔值）。关系：可通过 ProjectMembership 分配给多个项目。
- **Role（角色）**: 表示一组权限。属性：唯一标识符、名称、描述、是否系统预定义（布尔值）、创建时间戳。关系：可通过 ProjectMembership 分配给多个用户，包含多个权限绑定。
- **Permission（权限）**: 表示系统可以授权的操作。属性：唯一标识符、资源类型、操作名称（如 "tasks.delete"）。
- **RolePermission（角色权限）**: 角色和权限之间的多对多关系。属性：角色 ID、权限 ID。
- **ProjectMembership（项目成员资格）**: 用户与项目之间带角色的多对多关系。属性：用户 ID、项目 ID、角色 ID、加入时间。这是按项目访问控制的核心。
- **AuditLog（审计日志）**: 记录安全相关事件。属性：时间戳、用户 ID、事件类型、详情、IP 地址。

## 成功标准

### 可衡量成果

- **SC-001**: 用户可以在 2 分钟内完成注册。
- **SC-002**: 用户可以在 5 秒内完成登录。
- **SC-003**: 系统在 1 秒内正确拒绝 100% 的未授权访问尝试。
- **SC-004**: 所有角色和权限更改立即对后续请求生效。
- **SC-005**: 系统管理员可以在 3 分钟内配置具有权限的新角色。
- **SC-006**: 100% 的安全事件被记录，具有足够的审计详情。
- **SC-007**: 管理员可以在 30 秒内创建新用户账户并分配角色。

## 假设条件

- **认证方式**: 基于邮箱和密码的身份认证与会话管理。这是内部工具（如 Taskify）的标准方法。
- **会话管理**: 服务器端会话，会话令牌存储在 HTTP-only Cookie 中。这比本地存储替代方案提供更好的安全性。
- **密码要求**: 最少 8 个字符，至少一个字母和一个数字。这在安全性和可用性之间取得平衡。
- **角色范围**: 角色在两个级别运作 — 系统管理员（全局访问）和项目级角色（所有者、成员、访客）。项目级角色决定用户在特定项目内可以做什么。
- **多项目成员资格**: 用户可以通过 ProjectMembership 实体在不同项目具有不同角色。例如，用户在项目 A 中可能是成员，在项目 B 中是所有者。
- **单一管理员**: 系统中必须始终至少有一名系统管理员。系统将阻止移除最后一个管理员。
- **数据迁移**: 现有 User 表将被替换。预定义用户（张明、李伟等）将通过新凭据迁移或重新创建。
- **改造现有处理器**: 所有现有 API 处理器（项目、任务、评论）将添加身份认证和授权中间件进行改造。
- **邮箱验证**: 延期。注册时将邮箱标记为已验证以用于演示。密码重置和邮箱更改验证延期至 SMTP 基础设施可用时。
- **项目管理**: 完整 CRUD。项目创建者自动成为 Owner。Project Owner 可独立管理自己项目的所有成员，无需系统管理员介入。
- **前端范围**: 全部新增/替换。新增登录页、注册页、个人资料页、管理员后台（/admin）、项目管理页面。所有页面添加认证守卫。复用现有看板组件。
